# Rotate DB secrets (rotate-db-secrets.sh)

## Intent

Provide one generator for the database credentials used by the Compose stack: a manual, on-demand
tool (`project-tools/rotate-db-secrets.sh`) that creates or rotates `_01_rsc_wpm_backend/secrets/`
and the derived root `.env`, and applies the rotation to a LIVE database without recreating the
volume (via `ALTER USER`), then recreates the backend so it re-reads the new secret. Rotation is
**manual by design** (no cron), and **fail-closed**: if the live-stack conditions for a safe
rotation are not met, the script performs NO rotation and reports the situation found and what to
review. Hardcoding ends everywhere: `db-healthcheck.sh` loses its default credential and reads the
same secret source.

## Scope

- In: new `project-tools/rotate-db-secrets.sh` (modes `init`, `rotate [--check]`, `status`),
  `project-tools/db-healthcheck.sh` credential resolution (no plaintext defaults; read
  `secrets/db_user.txt` + `secrets/db_password.txt`, env overrides, fail-fast), root `.env`
  regeneration, FTD doc.
- Out: auto-rotation (cron/systemd) — explicitly NOT wanted; volume recreation as the destructive
  rotation path (only `container-management.sh`/manual stack teardown may do that); frontend
  credentials (the frontend has no DB credentials); secret managers (SOPS/Vault).

## Design decisions

- **Rotation on a live DB is `ALTER USER`, not rebuild.** Rebuilding/recreating the `postgres`
  container does not change the password on an existing volume (`pg_authid` is initialized once on
  an empty data directory). `container-management.sh rebuild-all` does not even touch `postgres`.
  The only non-destructive way to rotate on a live stack is:
  `docker compose exec postgres psql -U <user> -d wpm_db -c "ALTER USER <user> WITH PASSWORD '...'"`
  (official postgres image trusts local socket connections).
- **Fail-closed guardrail (user requirement).** `rotate` first evaluates conditions:
  secrets present, compose file present, postgres container running AND healthy. Any failure →
  per-condition diagnosis, "Rotation NOT performed", "review" instruction, exit 1, zero mutation.
  `rotate --check` runs only the condition evaluation (read-only).
- **Manual mode.** Rotation runs only when a human invokes it; no timers, no systemd units.
- **One source of truth.** `secrets/*.txt` are authoritative; `.env` and `db-healthcheck.sh` derive
  from them (script reads the files; `.env` is regenerated by `init`/`rotate`; values never printed).
- **Secret file mode 0644, NOT 0600 (container-readability).** Docker Compose `file:` secrets are
  bind mounts with **no uid/gid remapping**: the container user (uid 100 `bunuser`) reads the host
  file directly, so its mode must allow that uid. An owner-only `0600` file is unreadable inside the
  container; `readSecretFile` in `postgres.ts` then silently falls back to an empty password, and
  every DB query fails with `SASL: SCRAM-SERVER-FIRST-MESSAGE: client password must be a string` →
  `/health` 503. The secrets directory stays `0700` and the files are gitignored, so `0644` on the
  file itself is the pragmatic, correct choice for a local dev stack (host tools and the container
  user can both read it). `init`/`rotate` re-assert `0644` on every run.
- **Readiness wait before verifying.** Recreating the `backend` container is not instantaneous, so
  `rotate` polls `/health` for up to 30s instead of one immediate `curl` (the single-shot `curl`
  produced a false-negative `000`).
- **Order that converges.** rotate writes the new secret file + `.env` first, then `ALTER USER`,
  then recreates the `backend` container (compose secrets are runtime mounts, not baked into the
  image — no image rebuild needed), then verifies `/health`. If `ALTER USER` fails, the running
  stack is untouched and healthy; the script reports loudly and asks to re-run / review.

## Evidence

- `bash -n` clean on both scripts; both executable.
- `rotate-db-secrets.sh status` (read-only): secrets present (mode 0644), `.env` regenerated, postgres healthy, `/health` 200.
- `rotate-db-secrets.sh rotate --check` with the stack up: all 6 conditions `[ PASS ]`, exit 0.
- **Fail-closed proof (user guardrail):** with `postgres` stopped, `rotate --check` reports `[ FAIL ]` for the postgres conditions and prints "Rotation NOT performed — conditions are not met", "No secret file was changed and no database statement was run", "…the situation needs human review", exit 1. Postgres restarted afterwards; `/health` returned 200 and the stack was untouched.
- `rotate-db-secrets.sh init` idempotent: keeps existing files, refuses to overwrite without `--force`, regenerates `.env` (mode 600, derived from secrets, never prints values).
- Secret files kept at mode `0644` (container-readable; see the design note), `.env` at `0600`,
  `secrets/` dir at `0700`; `.env` and `secrets/` are git-ignored (`git check-ignore` confirms both).
- `db-healthcheck.sh`: no plaintext credential default; `grep admin123` → zero matches in both scripts. `./project-tools/db-healthcheck.sh` → **8/8 checks passed** (1 expected warning) with credentials resolved from `secrets/db_user.txt` + `secrets/db_password.txt`.
- `db-healthcheck.sh` fail-fast proof: with `db_password.txt` temporarily removed, it prints "No database password found. Set DB_PASS or PGPASSWORD, or create …/secrets/db_password.txt first (run ./project-tools/rotate-db-secrets.sh init to generate it)" and exits 1; file restored.
- **Live rotation executed (real stack) and a bug found + fixed.** The first real `rotate` applied
  the new password (`ALTER USER` OK, secret file 44 bytes) but `/health` returned 503. Root cause:
  the secret files had been set to `0600`, so the backend (uid 100 `bunuser`) could not read the
  bind-mounted file; `readSecretFile` fell back to an empty password and pg raised
  `client password must be a string`. Fix: secret files are `0644` (`SECRET_FILE_MODE`), re-asserted
  by `init`/`rotate` via `ensure_secret_modes`. After the fix, `/health` returned **200** and the
  data was intact (`Prueba` row present).
- **Verification sequence running the real green path:**
  1. `rotate` conditions → all 6 `[ PASS ]`.
  2. `ALTER USER` on live postgres (`8ec5480661a4…`) succeeded.
  3. backend recreated, `/health` → 200 after the readiness wait.
- **`init` copy corrected.** The closing hint no longer implies that restarting the stack re-applies
  credentials: it now states `init` only writes the files, that a brand-new empty volume reads them
  on first start, and that changing the password on an existing DB requires `rotate`.
- **Readiness-wait addition.** The single immediate `curl` in step 4 produced a false-negative `000`
  on recreation; step 4 now polls `/health` up to 30s (`wait_for_health`).
