# SKILL2: Comment Code File

## Purpose
Use this skill when you need to add clear, helpful comments to a code file so that a developer can understand the code, the intent behind it, the architectural decisions, and the reasoning for non-obvious implementation choices.

This skill is designed to produce documentation that is useful for both new contributors and experienced engineers reviewing the file later. The goal is not to add noisy comments everywhere, but to add high-value explanations where the code would otherwise be difficult to understand.

## Core objective
Review the target file and add comments that:
- explain what the code is doing at a high level
- explain the purpose of each major section or block
- clarify the intent behind decisions and trade-offs
- document non-obvious logic, configuration, and patterns
- describe why a design choice exists when the code alone does not make it obvious
- make the file easier to maintain and onboard to

## Best practices to follow

### 1. Explain intent, not just mechanics
Prefer comments that answer “why” and “what problem this solves” instead of only repeating the code.

Good:
- "This middleware validates the JWT before allowing access to protected routes so unauthenticated requests are rejected early."

Weak:
- "Check if token exists. If not, return error."

### 2. Add section-level paragraph comments
For each logical section of the file, add a short paragraph comment that explains the big picture before the code block starts.

Examples:
- "This section configures the HTTP server and defines the route registration flow. It centralizes startup logic so the app exposes the same API contract regardless of runtime environment."
- "The database layer is initialized here to provide a single shared connection for repository access. This keeps configuration concerns out of business logic and makes testing easier."

### 3. Add comments to important lines or blocks
Add comments near key logic such as:
- configuration setup
- environment variables
- dependency wiring
- request validation
- authentication and authorization
- error handling
- retry or fallback logic
- initialization sequences
- cross-service communication
- complex conditionals or edge-case handling

### 4. Explain design decisions
Where the code chooses one approach over another, document the decision briefly.

Examples:
- "Using a shared network instead of creating a duplicate Docker network keeps all services discoverable under the same project topology and avoids warnings during local test commands."
- "This retry loop is intentionally limited to three attempts to avoid pathological latency on upstream failures while still tolerating transient network blips."

### 5. Preserve clarity and avoid noise
Do not add comments to every single line. Prefer meaningful documentation over chatty repetition.

Good comments are:
- concise but informative
- relevant to the surrounding code
- easy to scan
- written in plain, professional language

Avoid:
- obvious comments that restate syntax
- redundant explanations for simple code
- outdated comments that do not match the implementation
- over-documenting trivial variables or assignments

### 6. Keep comments accurate and current
Comments must match the actual behavior of the code. If the implementation changes, update the surrounding comment so it stays trustworthy.

### 7. Use a layered commenting style
Use this structure when documenting a file:
- file-level overview comment
- section-level paragraph comments
- targeted comments for important blocks or lines
- comments explaining decisions, trade-offs, and edge cases

## Required output style
When applying this skill, the result should read like professional engineering documentation, not generic autogenerated comments.

The final comments should include:
- one overview comment for the file when useful
- one paragraph comment for each major section or feature area
- targeted inline comments for important logic, constraints, or decisions
- explanations of why the code is structured this way

## Prompt template
Use the following prompt when instructing an AI or assistant to comment a source file:

"Review this code file and add clear, useful comments that explain the code and the decisions behind it.

Requirements:
- Explain what the file does at a high level.
- Add paragraph comments before each major section to describe the big picture.
- Add targeted comments near important logic, config blocks, initialization, validation, auth, error handling, networking, or non-obvious behavior.
- Explain the reasoning behind architectural and implementation decisions, not just the syntax.
- Keep comments concise, professional, and easy to understand.
- Avoid noisy comments that merely repeat what the code already says.
- Do not add comments to trivial one-line operations unless they clarify a decision or edge case.
- Preserve the code’s original structure and behavior.
- If a design decision is implied by the code, state it clearly in plain language.
- For configuration or environment setup, explain why the chosen pattern matters.
- For complex logic, explain the purpose, trade-offs, and edge cases.
- Make the file easier for a new developer to understand without reading every line.

The output should read like a clean engineering document: concise explanatory comments, section-level summaries, and decision-oriented notes where they add real value."

## Short one-shot prompt
Use this compact version when a quick direct prompt is enough:

"Add comments to this code file to explain the code, the purpose of each section, and the important design decisions behind the implementation. Include a brief file-level overview, paragraph comments before major sections, and targeted comments for non-obvious logic, configuration, validation, initialization, error handling, or architecture choices. Explain why the code is structured this way, not just what each line does. Keep comments concise, clear, professional, and useful for future maintainers. Do not add noisy comments to trivial lines. Preserve the code’s behavior and structure."

## Recommended commenting structure
Use this pattern when commenting code files:

1. File header comment
   - summarize module purpose
   - mention major responsibilities
   - describe the system context if needed

2. Section header comments
   - explain intent and use case
   - describe boundaries between responsibilities
   - mention why this section exists in the design

3. Inline comments on complex blocks
   - explain non-obvious decisions
   - define edge-case handling
   - clarify why the logic is written this way

4. Decision notes
   - explain trade-offs and constraints
   - mention why a specific approach was chosen
   - highlight assumptions or risks if relevant

## Example of the desired style

"This module sets up the HTTP server and exposes the application routes. It centralizes startup configuration so the service can be bootstrapped consistently across local development, testing, and deployment environments."

"The request-validation layer is intentionally strict here to fail fast before business logic runs. This prevents invalid inputs from reaching downstream services and makes errors easier to diagnose."

"The retry helper uses a short, bounded timeout because upstream services sometimes fail transiently under load. Limiting retries keeps the system responsive while still tolerating brief network hiccups."

## Decision rules for this skill
When generating comments, favor these decisions:
- explain the purpose before the code
- anchor each section in the problem it solves
- explain trade-offs and constraints
- keep comments practical and maintainable
- avoid comments that sound like a copy of the code

## Final instruction
Apply these rules to the target file and produce comments that make the code readable, explain the design choices, and give the reader a clear mental model of the file. The comments should help someone understand both the code itself and the judgment behind how it was written.
